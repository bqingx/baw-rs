# Session lifecycle: generate → store → read → use → expire

Everything below is the behaviour of this tree (`src/auth.rs`, `src/auth_store.rs`,
`src/session.rs`, `src/client.rs`, `src/main.rs`). There is no keyring, no default
wallet, and no cross-directory fallback anywhere in this path.

## 1. Generation (`auth signin` → `auth verify`)

**Identity vs. session.** Two different things live in one file:

| value | what it is | generated by |
|---|---|---|
| `clientId` | stable client identity, UUID v4 shape from 16 bytes of `OsRng` | first `auth signin` in an absent directory |
| `sessionId` | the `agentSessionId` login cookie | only a completed `auth verify` |

Signin, in order:

1. `Store::open(dir, create=true)` — opens each path component with `openat(... O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC)`, creating **only the last** component with `mkdirat(0o700)`, then requires `st_uid == geteuid()` and mode `0700`, and takes an exclusive `flock` on the directory.
2. `credentials(instance, create=true)` — absent `session.json` ⇒ fresh `clientId`, encrypted, written with an empty `sessionId`. Existing file ⇒ decrypt, never regenerate, never migrate.
3. Ephemeral secp256k1 key (`k256`): the public key's compressed form minus its `02`/`03` prefix becomes `publicKeyHex` (64 hex chars); the secret is dropped immediately. No wallet signature key is stored anywhere.
4. `POST /bapi/defi/v1/public/wallet-direct/agent-wallet/login` with `{isFirstLogin:true, os, publicKeyHex}` ⇒ `qrCodeId`, `qrCodeUrl`, `expireAt`; the CLI prints those plus `pairingCode` = first 3 + last 3 hex of the public key. It never renders or opens a QR itself.
5. `auth-pending` is written (encrypted JSON: `client`, `cookie`, `baseline`, `qr_code_id`, `expire_at`), where `expire_at = min(server expireAt, signin start + 5 min)`. `session.json` is **not** touched.

Verify, in order:

6. Reads `auth-pending`, rejects if expired, or if `qrCodeId` / clientId / `session.json` sha256 baseline do not match.
7. Polls `POST .../login/confirm` every 2 s until `connectionStatus == CONNECTED`, then `GET .../login/query` until `CONNECTED` **and** `walletCreateStatus == CREATED`. The whole poll is wrapped in `timeout_at(deadline)`, so a stalled HTTP request is cancelled, and the 5-minute cap persists across separate `verify` invocations.
8. Commits with `save_cas(instance, client, sessionId, baseline)` — refuses if `session.json` changed meanwhile (stale-write protection). Empty cookie is an error (`confirmed login omitted session cookie`). Then `auth-pending` is removed.

`--confirm --operation-id` is required for every auth command, and consent is checked
before the directory is even opened.

## 2. Storage

Directory `<wallet-dir>`: mode `0700`, owner-only, no symlink component, exclusive
`flock` for the duration of a command.

`session.json`: regular file, `0600`, `st_nlink == 1`, ≤ 1 MiB, opened
`O_NOFOLLOW|O_NONBLOCK` and opened **relative to the checked directory fd** (never by
re-resolving the path).

```json
{ "clientId": "<base64 IV|ciphertext|tag>", "sessionId": "<base64 IV|ciphertext|tag>" }
```

- Cipher: AES-256-GCM, 16-byte IV, `base64(IV ‖ ciphertext ‖ tag)`.
- Key: `PBKDF2-HMAC-SHA256(password=instance, salt="baw-agentic-wallet-v1:"+instance, 100_000)` — the instance string **is** the credential.
- Legacy plaintext UUID `clientId` is accepted for reading and is never rewritten by a query.
- Writes: temp `.auth-<16B hex>` created `O_CREAT|O_EXCL|O_NOFOLLOW` `0600` → `write_all` → `sync_all` → `renameat` in the same directory (atomic replace) → directory `fsync`; on any error the temp file is `unlinkat`'d.
- `auth-pending`: same encryption, same directory, exists only while a login is pending.
- `.baw-rs-operations/` holds mutation intent journals — digests and identifiers, never credentials, cookies or signatures.

Empirically, with the built binary:

```text
dir 0755                      -> session directory must be private (0700)
dir 0700, no session.json     -> cannot open session file
session.json garbage          -> invalid encrypted credential
session.json 0644             -> session file must be private (0600)
```

## 3. Reading

`src/main.rs` picks one of two paths per command: `auth *` → `auth::bootstrap`
(may create), everything else → `session::load(dir, instance)` (never creates).
`serve` loads once and keeps it in-process; `--warm` clients hit the socket and the
server hands out the already-loaded session.

`load` fails closed on: absolute/parent-dir components, any symlink, wrong owner,
non-`0700` dir, non-`0600`/multi-link/non-regular/oversized file, non-`{` first
non-whitespace byte, undecryptable ciphertext, non-printable decrypted bytes, or a
`clientId` that is not UUID-shaped. Nothing is repaired, migrated or guessed.

## 4. Use on the wire

- Every request sends `cookie: agentSessionId=<sessionId>` (built as a sensitive `HeaderValue`) **unless** the session is empty, plus `agentclientid` and `bnc-uuid` headers carrying `clientId`, and a random `x-trace-id`.
- An empty `sessionId` is the legitimate logged-out native state: `wallet status` answers `{"status":"UNCONNECTED"}` locally without any network call; other commands reject it.
- HTTP 401/403, or an API `code` in `{100001005, 10003001, 10003002}`, calls `invalidate()`: memory flag set, cookie zeroized, that process refuses further requests with `session invalidated; restart with a valid session`. **Disk is not touched.**
- A rotated `Set-Cookie: agentSessionId=…` is adopted in memory only, and only after the response parsed as a valid API envelope. Only `auth verify` ever persists a cookie to disk.

## 5. Expiry and logout

`auth signout`: one bodyless `POST .../login/logout` → `invalidate()` → `save_cas`
writing `sessionId: ""` while **preserving** `clientId` → remove `auth-pending`.
A remote failure still clears local state and reports
`local session cleared; server logout uncertain` rather than claiming success.

## Portability: nothing is bound to this machine

Encryption and decryption use **only** the instance string:

```text
key = PBKDF2-HMAC-SHA256(instance, "baw-agentic-wallet-v1:" + instance, 100_000)
```

No hostname, MAC address, CPU id, machine-id file, keyring, TPM or user id participates.
The consequences, stated plainly:

- Copying a wallet directory to another machine and supplying the same instance string
  decrypts it there. That is intended (it is how a session is portable at all), and it is
  also why the instance string is a credential.
- Nothing needs to be "activated" per device; there is no device registry.
- Proof in-tree: the `SESSION` / `CLIENT` ciphertexts in `src/session.rs` tests were
  generated by an independent Python script from the instance string alone. They decrypt
  here, which is only possible because no machine-specific input enters the key.
- The flip side is unchanged and fail-closed: wrong instance ⇒ `invalid encrypted
  credential`, file untouched, no repair, no migration.

## Known gaps (tracked, not yet fixed)

- **Rotated cookies are not persisted.** After a query rotates the cookie, a later
  cold process presents the older on-disk cookie. If the backend invalidates the
  rotated-from value, that run fails with `session expired` and needs a fresh
  `auth verify`. Rotation persistence is deliberately conservative (only verified auth
  commits) but this is a real operational gap, not a design claim.
- **A crashed signin leaves `auth-pending`.** It is honoured until `expire_at`, so a
  retry is refused with `authentication already pending` even though no verify will
  ever run. Recovery today is `auth signout` or waiting out the cap.
- **No renewal**: nothing proactively re-verifies an expired session; the operator must
  re-run `auth verify` after a new `auth signin`.
- **Live path unverified**: no QR scan, no real signature, no swap/transfer has been
  executed against a real account from this tree.
